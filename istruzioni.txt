1) Due parole su GitHub e Render

GitHub = il repository del codice. È solo “il posto dove vive il codice” e da cui Render prende i file ad ogni push.
Render = la piattaforma che esegue il tuo backend (e serve il tuo frontend statico). A ogni git push su main, Render ricostruisce e (se tutto ok) redeploya i servizi.


In breve: scrivi/modifichi → git push su GitHub → Render prende il codice e aggiorna backend/frontend online.


2) Dove finiscono i dati oggi? (SQLite vs MySQL)

In locale (sul tuo PC), quando avvii il backend, i dati vanno in D:\Python\FP_Other\FPFood\data\fpfood.db (SQLite locale).
Su Render, i dati vanno nel file SQLite sul server Render, nel percorso data/fpfood.db del container.

Non si aggiorna GitHub con i dati. GitHub non è un DB.
Il file su Render non è lo stesso della tua macchina: sono due ambienti diversi, ognuno con il suo fpfood.db.
Piano Free: i container possono “addormentarsi”, ma i file della Build restano; i file scritti in runtime su filesystem possono essere effimeri (non garantiti nel lungo periodo). Per questo, in produzione si usa MySQL o Postgres gestito. (Tranquillo: ora testiamo; la migrazione a MySQL è nel piano sotto.)

Fase C – Dati aziendali
6) Migrazione a MySQL (server principale)

Switchiamo il backend da SQLite a MySQL (connector pymysql o mysql-connector-python).
Varianti:

Switch diretto: cambi il layer DB e da domani tutti i nuovi pasti finiscono su MySQL.

Dal tuo gestionale: solo GET REST (/api/pasti/{utente}, /api/pasti/{utente}/totale) e importi in MySQL/DB principale secondo le tue regole.
Se vorrai, creo endpoint “report per periodo” (/api/pasti?from=...&to=...).




4) Risposte puntuali alle tue domande

“Dopo il salvataggio, i dati vanno su fpfood.db (SQLite)? Lo vedo su GitHub?”

Sì, oggi i salvataggi vanno su SQLite: in locale nel tuo D:\..., su Render nel filesystem del servizio backend.
No, GitHub non si aggiorna con i dati. GitHub contiene solo codice, non è un DB.


“Lo vedo anche in locale (D:)?”

Solo quando usi il backend locale: allora aggiorni il tuo data/fpfood.db locale.
Quando usi la PWA online che punta a Render, aggiorni il db su Render, non quello locale.


“Tool che migra da SQLite a MySQL?”

Semplice script Python: legge da SQLite (sqlite3), inserisce su MySQL (pymysql/mysql-connector-python).
In alternativa, direttamente da MySQL con LOAD DATA (se esportiamo CSV) o con SQLAlchemy per una migrazione più “tipata”.
Te lo preparo con F&R quando dici “OK Migrazione”.

Mini‑FAQ velocissima

Serve ricompilare quando cambio frontend?
Su Render Static Site: ogni git push → redeploy automatico. Se cambi service-worker.js / manifest, fai hard refresh o “Clear site data” per vedere subito gli aggiornamenti.
Il piano Free di Render “dorme”?
Sì, può addormentarsi: il primo hit dopo un po’ è più lento. In produzione reale conviene un piano non‑sleep o un DB esterno (MySQL) e un ping periodico.
